# Shipping a trial / demo variant of an app that normally needs a backend

Use when the user wants to **try the app on a real phone today**, but the app's normal path needs a
server that does not exist yet (no backend, no account, no API). The deliverable is a second APK
that runs standalone, installs alongside the real one, and cannot be mistaken for it.

This is a build-variant problem, not a UI problem. Solve it with a build type, not `if (demo)`
branches scattered through the UI.

## Decide the variant shape before writing code

| Approach | Verdict |
|---|---|
| Turn demo mode on in `release` | **No.** A money/credential app must never ship a path that marks a payment settled, or a login, without the server. That is a real hole in the production artifact. |
| Demo mode only in `debug` | **No — and this is the trap.** The APK you hand the user is built `release` (see `app-performance-and-release-build.md`: the shipped build type is invisible from the source tree). Debug-only demo code is dead in the artifact users install, so login fails exactly as before. |
| **A separate `demo` build type** | **Yes.** Distinct `applicationId` (installs side by side), release signing, a compile-time flag, and a label that says Demo. |

## 1. Define the build type

```kotlin
buildTypes {
    release {
        isMinifyEnabled = true
        isShrinkResources = true
        signingConfig = signingConfigs.findByName("release")
        buildConfigField("boolean", "DEMO_MODE", "false")
    }
    create("demo") {
        initWith(getByName("release"))          // same R8 + signing as release
        isDebuggable = false                    // NOT a debug build
        applicationIdSuffix = ".demo"           // side-by-side install
        versionNameSuffix = "-demo"
        buildConfigField("boolean", "DEMO_MODE", "true")
        manifestPlaceholders["appLabel"] = "<App> (Demo)"
    }
}
```

- **`initWith(release)` then flip only what differs** — the demo must be minified and release-signed,
  otherwise you are shipping a debuggable APK (`run-as` reads stored tokens).
- **`buildConfigField`, not a hand-written constant.** The flag is baked at compile time so R8 can
  dead-strip the demo path out of `release` entirely (prove it in step 4).
- **`manifestPlaceholders["appLabel"]` + `android:label="${appLabel}"`** so the launcher shows
  "(Demo)". Two identical icons on one home screen is how the user installs the wrong one.
- **`applicationIdSuffix`** so it coexists with the real app instead of replacing it.

## 2. Read the flag through expect/actual, and do NOT reach for `BuildConfig.DEBUG`

`BuildConfig.DEBUG` is **not generated by default since AGP 8.0** — using it fails to compile unless
`buildFeatures.buildConfig = true`. Read your own field instead:

```kotlin
// commonMain
expect val isDemoBuild: Boolean

// androidMain
import <app.package>.BuildConfig            // the generated class is in the app's package, NOT yours
actual val isDemoBuild: Boolean get() = BuildConfig.DEMO_MODE

// iosMain — a Kotlin/Native build has no BuildConfig; keep it false and say why
actual val isDemoBuild: Boolean get() = false
```

The generated `BuildConfig` lives in the **module's applicationId package**; a file under
`core/platform/` must import it by full path. A missing import here is one of the recurring
"type I forgot to create/import" errors — run the dangling-import check before pushing
(`scripts/check-dangling-imports.py`).

## 3. Put a SEAM at the network boundary, not `if (demo)` in the UI

Introduce interfaces at the boundary the demo replaces, then swap the implementation:

```kotlin
interface SalesGateway { suspend fun createSale(...): Sale }
interface SignalGateway { suspend fun send(signal: PaymentSignal) }

class ApiSalesGateway(private val api: SalesApi) : SalesGateway { ... }
object DemoSalesGateway : SalesGateway { /* canned data, in-memory */ }
```

- The production path stays exactly as it was; only the construction site picks an implementation.
- **Bonus that pays for the refactor: the controller becomes testable without a network.** A
  controller that took a concrete `SalesApi` could not be unit-tested; one that takes a gateway can.
  Expect the test count to rise as a side effect — that is the proof the seam is real.
- **The demo banner must not be dismissible.** A persistent "MODE DEMO" strip is the difference
  between a demo and a user believing a fake payment is real.

## 4. Gate the flag in CI, and prove the demo code is ABSENT from release

The whole point is that demo code must not exist in the production artifact. Assert both directions:

```yaml
- name: Gate DEMO_MODE
  run: |
    set -e
    rel=$(find composeApp/build/generated -name BuildConfig.java -path '*release*' | head -1)
    dem=$(find composeApp/build/generated -name BuildConfig.java -path '*demo*'    | head -1)
    grep -q 'DEMO_MODE = false' "$rel" || { echo "::error::release DEMO_MODE must be false"; exit 1; }
    grep -q 'DEMO_MODE = true'  "$dem" || { echo "::error::demo DEMO_MODE must be true";    exit 1; }
    echo "release: false . demo: true" >> "$GITHUB_STEP_SUMMARY"
```

Make the `BuildConfig.java` search **path-tolerant** (`-path '*release*'` on the `find`, not a
hardcoded generated-source directory) — the generated path moves between AGP versions and a
hardcoded one silently matches nothing, so the grep passes on an empty string.

Then prove it on the **artifacts**, not the flag. Extract each APK's dex and grep for a string that
only the demo path can produce (the banner text, a canned product name, a fake token):

```bash
for v in release demo; do
  mkdir -p dx_$v && unzip -o -q composeApp/build/outputs/apk/$v/*.apk 'classes*.dex' -d dx_$v
  echo "$v: $(strings dx_$v/classes.dex | grep -c '<demo-only-string>')"
done
# demo: >=1   release: 0
```

- **A release count of 0 is the deliverable** — it proves R8 dead-stripped the demo path, not merely
  that it is unreachable at runtime.
- **Do not be alarmed when the two APKs are nearly the same size.** R8 inlines the boolean constant
  and the dex is compressed, so a difference of a few bytes is normal; the *string* evidence is what
  settles it, not the byte count. A large size gap would instead suggest demo code survived.

## 5. The release script must refuse a variant whose applicationId does not match

One script publishing both variants will happily upload a `demo` APK to the production filename (or
the reverse) because the build output path and the published name are independent. Gate it:

```bash
case "$VARIANT" in
  release) expect="id.example.app";        prefix="App" ;;
  demo)    expect="id.example.app.demo";   prefix="App-demo" ;;
esac
actual=$(aapt2 dump badging "$APK" | sed -n "s/^package: name='\([^']*\)'.*/\1/p")
[ "$actual" = "$expect" ] || { echo "APK is '$actual', expected '$expect' for $VARIANT"; exit 1; }
```

Read the applicationId from the APK with `aapt2 dump badging`, never from the build file — the build
file is the intent, the APK is the fact. Derive the published filename from the variant so the demo
APK can never overwrite the production one (`<App>-<ver>.apk` vs `<App>-demo-<ver>.apk`), and keep
`update.json` pointing only at production.

## 6. The download page must distinguish the two, honestly

If the production backend is not built yet, the **demo is the only thing that actually works** — so
the page should lead with it and say plainly that the full version needs a server that is not ready.
Two download buttons with one-line "you need an account" / "no account needed" labels beat a single
button that installs something that cannot log in.

## Close out honestly

What static evidence CAN prove: the flag is correct in both variants, the demo-only strings exist
only in the demo dex, both APKs are release-signed and non-debuggable, and the demo installs
side-by-side.

What it CANNOT prove: **that the demo flow actually runs on a device.** "Login with any email and
reach the cashier" has not happened until someone taps it on a real phone. Say that explicitly —
do not report a demo as working from a green build and a dex grep.
